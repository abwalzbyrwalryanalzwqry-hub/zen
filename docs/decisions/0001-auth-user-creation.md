# القرار 0001: إنشاء حسابات اسم المستخدم من SQL، مع حرّاس

- **التاريخ:** أكتوبر 2026 (تدقيق أكتوبر، المرحلة 3.1)
- **الحالة:** معتمد، ويُراجع عند أول ترقية كبرى لـ Supabase Auth أو قبل تجاوز 5,000 حساب.

## السياق

`register_username_account` و`teacher_create_student` يكتبان صفوف `auth.users` و`auth.identities` مباشرة،
و`_set_auth_password` يحدّث `encrypted_password`. هذا يربط زِن بتفاصيل داخلية في مخطط GoTrue: إن أضاف Supabase
عموداً إلزامياً أو غيّر صيغة الهوية، يتعطّل التسجيل بصمت. اقترح التقرير نقل ذلك إلى دالة Edge تستعمل
`auth.admin.createUser` / `updateUserById` مع فحص التسريبات.

## الخيارات

| الخيار                                 | المزايا                                                                                                      | العيوب                                                                                                                                          |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| أ. دالة Edge `zen-auth` بواجهة الإدارة | واجهة مستقرة موثّقة، لا كتابة في مخطط auth                                                                   | يعيد كتابة أهم مسار في التطبيق؛ حدود المعدّل حسب IP تحتاج نقلاً موثوقاً لعنوان العميل عبر Edge؛ نشر ومفتاح خدمة إضافيان؛ لا يُختبر في `test:db` |
| ب. البقاء على SQL مع حرّاس             | مسار مختبَر (`test:db` فحوص 1–125) ويعمل اليوم؛ ذرّي (المستخدم واسم المستخدم ورمز الاسترداد في معاملة واحدة) | الاعتماد على مخطط auth يبقى                                                                                                                     |

## القرار

**ب**، مع ثلاثة حرّاس تُغلق أخطر ما في الاعتماد:

1. `auth_schema_guard()` في النسخ الاحتياطي اليومي: يفشل إن ظهر في `auth.users` أو `auth.identities` عمود
   إلزامي بلا قيمة افتراضية لا تكتبه دوالنا — يُكتشف التغيير خلال يوم، قبل المستخدمين.
2. سير **Staging** الأسبوعي (`scripts/staging-smoke.mjs`): تسجيل حقيقي ثم دخول عبر GoTrue نفسه، فأي عدم توافق
   في الهوية أو التجزئة يظهر هناك أولاً.
3. كلمات المرور: الخادم يرفض الشائعة (`private.common_passwords`) في كل مسارات التعيين، والتطبيق يفحص
   التسريبات بـ k-anonymity قبل الإرسال (إرشادي، يفشل مفتوحاً). Leaked Password Protection في لوحة Supabase
   لا يغطّي هذه المسارات لأنها لا تمرّ بـ GoTrue.

## متى ننتقل إلى أ

أيّ مما يلي: فشل `auth_schema_guard` أو دخان Staging بسبب تغيير في Auth؛ حاجة إلى MFA أو تسجيل اجتماعي؛
ترقية إلى خطة Pro مع دعم رسمي. خطة الانتقال: دالة `zen-auth` بـ `register` و`reset` تستدعي `auth.admin`،
ثم دالة SQL للخادم فقط تكمل اسم المستخدم ورمز الاسترداد، ثم سحب `EXECUTE` من anon على الدالتين القديمتين
في ترحيل لاحق بعد أسبوع من النشر.
